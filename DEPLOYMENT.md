# Зачётка: новые функции и хранение данных

Это полный проект со всеми основными разделами: скрытые материалы, защищённые файлы, фильтры архива, лимит 20 МиБ, серверное избранное, личные оценки билетов и режим случайного билета, помодоро с сохранением остатка и историей завершённых сессий, изменение группы, резервные копии.

## Установка полного проекта

1. Сохраните существующую БД и папку с загруженными материалами **до** обновления.
2. Замените исходники в вашей ветке файлами из полного ZIP. `manage.py`, `config/`, `accounts/`, `materials/`, `tickets/`, `timer/`, `templates/`, `static/` и миграции уже входят в архив.
3. Установите зависимости: `python -m pip install -r requirements.txt`.
4. Примените миграции: `python manage.py migrate`.
5. На сервере выполните `python manage.py collectstatic --noinput`, если статика отдаётся Nginx/WSGI-хостингом.
6. Задайте секреты окружения и создайте администратора командой `python manage.py bootstrap_admin`.
7. Запустите приложение обычным способом. Для продакшена обязательно настройте HTTPS, переменные окружения, постоянное хранилище и веб-сервер.

**Важно:** никаких пользователей, групп или материалов нельзя получить обратно только из GitHub. Уже существующий файл `db.sqlite3` **нельзя удалять** при обновлении. Миграции сохраняют старые записи и добавляют поля/таблицы.

## Администратор

Логин по умолчанию для `bootstrap_admin` — `admin676967`. Задайте пароль из задания безопасно через переменную окружения `ADMIN_PASSWORD` и выполните:

```powershell
# Windows PowerShell: укажите значение вашего пароля вместо троеточия.
$env:ADMIN_USERNAME = 'admin676967'
$env:ADMIN_PASSWORD = '...'
python manage.py bootstrap_admin
Remove-Item Env:ADMIN_PASSWORD
```

```bash
# Linux/macOS: не храните секрет прямо в репозитории, укажите через переменную окружения.
export ADMIN_USERNAME='admin676967'
read -rsp 'ADMIN_PASSWORD: ' ADMIN_PASSWORD; echo
export ADMIN_PASSWORD
python manage.py bootstrap_admin
unset ADMIN_PASSWORD
```

Админка: `/admin/`. Учётная запись создаётся в **текущей БД** с хешем пароля, повторный запуск обновляет её. Не записывайте реальный пароль в README, код, git или публичный лог.

## Как сделать хранение постоянным

Сейчас Django использует SQLite по умолчанию. Если размещаете сайт на компьютере или сервере с **постоянным диском**, можно оставить SQLite:

```bash
export DATA_DIR=/srv/zachetka-data
export MEDIA_ROOT=/srv/zachetka-data/media
export BACKUP_DIR=/srv/zachetka-backups
```

Перед первым запуском создайте каталог DATA_DIR и выдайте права пользователю, под которым работает сайт. `db.sqlite3`, `media/` и резервные копии должны находиться **в постоянных каталогах** (при перезапусках, redeploy и удалении контейнеров не исчезают). Не коммитьте их в Git.

На хостингах с временной файловой системой (например, без подключённого volume) `DATA_DIR` в корне приложения **не обеспечивает** сохранность при повторном развёртывании. Для надёжного хранения пользователей, групп и билетов используйте управляемый PostgreSQL и **постоянный том/объектное хранилище** для media, например:

```bash
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/DBNAME'
export DB_SSLMODE=require
export MEDIA_ROOT=/mnt/persistent/media
export BACKUP_DIR=/mnt/persistent/backups
```

Учтите: PostgreSQL сам сохраняет данные только пока существует ваш экземпляр БД; бесплатная база может быть удалена поставщиком. Резервные копии нужно дополнительно вывозить во внешнее хранилище. Данный код не создаёт тома или базу у хостера автоматически.

Для production задайте также:

```bash
export DJANGO_DEBUG=0
export DJANGO_SECRET_KEY='длинный_постоянный_случайный_секрет'
export DJANGO_ALLOWED_HOSTS='example.com,www.example.com'
export DJANGO_CSRF_TRUSTED_ORIGINS='https://example.com,https://www.example.com'
```

## Доступ к файлам

Архив `/materials/`, загрузка и выдача `/materials/<id>/file/` доступны только после входа. Старые ссылки вида `/media/materials/...` не должны выдавать файлы **ни из Django, ни через Nginx/Apache/CDN**. В `config/urls.py` публичная раздача отключена. Если используете Nginx, перенесите директивы из `deploy/nginx-zachetka.conf.example` в свой `server { ... }`: `location /media/ { return 403; }`. **Не** настраивайте `alias`/`root` для публичной раздачи MEDIA_ROOT и не раздавайте файлы через отдельный публичный bucket URL.

Новые ссылки в архиве `/materials/<id>/file/` проверяют вход и `is_hidden` **на каждом запросе**. Флаг «Скрыт» меняется в `/admin/materials/material/`. Скрытый материал возвращает HTTP 404, даже если известен его ID. Старые ссылки на файлы не предназначены для скачивания: переходите из обновлённого архива.

Файл размером более 20 МиБ отклоняется формой Django и валидатором модели. Остальные введённые поля сохраняются после ошибки. На Nginx установите `client_max_body_size 25m` — это отдельный общий лимит размера HTTP-запроса; размер **самого файла** в Django ограничен строго 20 МиБ. При лимите Nginx < 20 МиБ сервер может показать свою страницу 413 вместо ошибки формы.

## Ежедневное резервное копирование (НФТ-06)

Скрипт `python scripts/backup.py` делает консистентный снимок SQLite (через SQLite Backup API) либо PostgreSQL (`pg_dump`, нужен установленный `postgresql-client`) и добавляет текущие файлы из MEDIA_ROOT в ZIP. Сохраняет **семь последних успешных** архивов, более старые удаляет. Важно: если MEDIA_ROOT интенсивно изменяется во время резервного копирования, желательно на время копии приостановить новые загрузки.

Пример Linux cron, каждый день в 03:00 по времени сервера:

```cron
0 3 * * * cd /srv/zachetka && /srv/zachetka/venv/bin/python scripts/backup.py >> /srv/zachetka-backups/backup.log 2>&1
```

Переменные DATA_DIR, DATABASE_URL, MEDIA_ROOT, BACKUP_DIR должны быть доступны процессу cron (например, через закрытый для посторонних файл переменных окружения или systemd service). Самостоятельно запущенный скрипт **не** ставит расписание: добавьте запись cron или задачу в планировщике хостинга. Проверяйте периодически лог и реальное восстановление.

## Как восстановить сайт из копии

1. **Остановите сайт**, чтобы новые записи не шли в БД/файлы.
2. Сохраните отдельную копию текущих данных, даже если они повреждены.
3. Для SQLite на локальной машине укажите прежние `DATA_DIR` и `MEDIA_ROOT`, затем выполните:

```bash
python scripts/restore.py /path/to/backups/zachetka-YYYYMMDD-HHMMSS-XXXXXX.zip
python manage.py migrate
python manage.py runserver
```

4. Для PostgreSQL сначала распакуйте ZIP в отдельный каталог, восстановите файл `database.dump` в **пустую** базу данных:

```bash
pg_restore --clean --if-exists --no-owner --dbname='postgresql://USER:PASSWORD@HOST:5432/DBNAME' database.dump
```

Затем перенесите содержимое `media/` из ZIP в ваш MEDIA_ROOT, выполните `python manage.py migrate` и запустите сайт. Пароль БД не храните в истории shell — используйте переменные окружения либо файл `.pgpass`.

5. Проверьте регистрацию/вход старых пользователей, список учебных групп, материалы и скачивание файлов. Если использовали другой `DJANGO_SECRET_KEY`, старые сессии могут завершиться, но учётные записи останутся.

**Проверка числа копий:** `ls -1 /srv/zachetka-backups/zachetka-*.zip | wc -l` (должно быть не более 7 после первого запуска скрипта).

## Таймер и случайные билеты

В `/tickets/` оценка «Не знаю», «Плохо» или «Выучил» сохраняется для каждой пары пользователь–билет в БД. При выборе случайного билета сначала выбираются «Не знаю» и «Плохо»; билеты «Выучил» начинают выпадать только после изучения всех остальных. На странице случайного билета есть таймер подготовки на 1–60 минут (по умолчанию 15).

В `/timer/` досрочное переключение «Работа → Перерыв → Работа» сохраняет оставшиеся секунды обоих режимов. Состояние хранится в localStorage **для текущего браузера и пользователя**, включая восстановление после перезагрузки страницы. Это не синхронизация помодоро между телефонами/компьютерами. Все пользователи, учебные группы, избранное, статусы билетов и завершённые рабочие сессии, напротив, хранятся в БД.
